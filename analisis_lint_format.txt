> que es el baseline?

▸ Thought for 6s, 434 tokens
  Defining the Baseline Concept
  El baseline (línea base) en herramientas de análisis estático como Detekt es un archivo (generalmente baseline.xml) que funciona como una "foto" o registro de todos
  los errores y advertencias de código preexistentes en el proyecto en un momento determinado.
  ──────
  ### ¿Para qué sirve?

  Cuando incorporas Detekt a un proyecto que ya tiene mucho código escrito, es común que detecte decenas o cientos de problemas existentes (métodos largos, números
  mágicos, complejidad ciclomática, etc.). Corregirlos todos juntos de inmediato suele ser inviable y frenaría el desarrollo.

  El baseline soluciona esto:

  1. Registra los problemas actuales: Guarda una lista con los errores preexistentes.
  2. Ignora los errores conocidos: Detekt no hará fallar la build por los errores que ya están registrados en el baseline.
  3. Bloquea errores nuevos: Si alguien escribe código nuevo o modifica código existente e introduce un nuevo code smell, Detekt sí fallará y obligará a corregirlo.
  ──────
  ### ¿Cuál es la ventaja?

  • Adopción gradual: Te permite activar reglas estrictas de calidad de código de inmediato sin tener que refactorizar todo el proyecto en un solo día.
  • Detiene la degradación: Asegura que a partir de hoy el código nuevo cumpla con los estándares, mientras la deuda técnica vieja se puede ir corrigiendo
  paulatinamente.
  ──────
  ### ¿Cómo se usa?

  • Crear / Actualizar: Ejecutas ./gradlew detektBaseline para generar el archivo baseline.xml.
  • Versionar: Se sube a Git (git add config/detekt/baseline.xml) para que todo el equipo y el CI/CD utilicen la misma referencia.

  Analyzing Build Side Effects
  No se incluye el formateador (ktlintFormat) dentro de la tarea build por varias razones fundamentales de diseño y buenas prácticas de ingeniería de software:
  ──────
  ### 1. Principio de verificación vs. corrección (Efectos secundarios)

  • build debe ser de solo lectura / verificación: El objetivo de build es compilar, correr tests y verificar calidad. Debe ser un proceso idempotente y predecible.
  • El formateador muta el código: ktlintFormat modifica físicamente los archivos .kt en el disco. Si build formateara automáticamente, cambiaría tu código fuente
  silenciosamente mientras compila, dejando modificaciones sin commitear en tu espacio de trabajo sin que lo notes explícitamente.
  ──────
  ### 2. Problemas en CI/CD (Integración Continua)

  • En un pipeline de CI (como GitHub Actions), el servidor descarga el commit que creaste.
  • Si build modificara los archivos en el servidor de CI:
      • La build "pasaría" en el runner porque los archivos se corrigieron en memoria/disco temporal del servidor.
      • Sin embargo, el repositorio en GitHub seguiría teniendo el código mal formateado.
  • Por eso, en CI se usa la regla: si el código no vino ya formateado desde la máquina del desarrollador, la build de CI debe fallar, no auto-corregirse.
  ──────
  ### 3. Invalida la caché de Gradle (Build Cache)

  • Gradle utiliza hashes del código fuente para saber si una tarea está UP-TO-DATE y evitar compilar cosas que no cambiaron.
  • Si una tarea dentro de build modifica los archivos fuente .kt de entrada, invalida la caché incremental, haciendo que los builds sean mucho más lentos.
  ──────
  ### 4. ¿Dónde sí debe ir el formateador?

  El formateo debe ser una acción previa o explícita:

  1. En el IDE: Al guardar el archivo (Ctrl + S / Cmd + S).
  2. Como comando manual: Cuando el desarrollador corre ./gradlew ktlintFormat.
  3. En los Git Hooks (Pre-commit): Justo antes de que el código se guarde en Git (como ya está en pre-commit), donde se formatea y se avisa al desarrollador si hubo
  cambios antes de confirmar el commit.

  Clarifying Task Differences
  En Gradle, las tareas check y build son parte del ciclo de vida estándar y tienen propósitos distintos pero complementarios:
  ──────
  ### 1. Tarea check (Verificación)

  • Objetivo: Responder a la pregunta: «¿El código está sano y cumple todos los estándares de calidad?»
  • Qué hace: Ejecuta únicamente tareas de validación y análisis. No empaqueta ni genera archivos finales (.jar).
  • Qué incluye típicamente:
      • Tests unitarios y de integración (test).
      • Linters y análisis estático (detekt, ktlintCheck).
      • Verificación de cobertura de código (jacocoTestCoverageVerification).

  ──────
  ### 2. Tarea build (Construcción completa)

  • Objetivo: Responder a la pregunta: «¿El código está sano Y podemos generar el paquete final listo para usar o publicar?»
  • Qué hace: Es la tarea más completa. Engloba todo check más el empaquetado del proyecto.
  • Fórmula clave:

    build = assemble + check
